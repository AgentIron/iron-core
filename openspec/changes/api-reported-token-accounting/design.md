## Context

`iron-core` currently estimates token usage from text size in multiple places: active context snapshots, durable `uncompacted_tokens`, compaction metrics, post-turn pressure checks, handoff sizing, and model-switch adaptation. That estimate is cheap and always available, but it drifts as sessions grow and becomes least reliable when the runtime most needs accurate pressure information.

`iron-providers` 0.2.9 exposes normalized `ProviderEvent::Usage { usage: TokenUsage }` events. Provider-reported `input_tokens` are the best available count of the provider-visible prompt that was just sent. This lets `iron-core` replace full-context heuristic accounting with a baseline-plus-delta model.

The key semantic constraint is that provider `input_tokens` describe request input, not the response content generated after that request. Assistant output and assistant tool-call blocks produced during a response must remain part of the local delta for the next request until a later usage-bearing response establishes a new input baseline.

## Goals / Non-Goals

**Goals:**

- Use provider-reported input tokens as the preferred baseline for current context estimates.
- Bound heuristic error to locally added deltas after the latest usage baseline.
- Track provider-reported accumulated input, output, cached-input, cache-creation, cache-read, and reasoning-output usage for telemetry and future cost accounting.
- Preserve heuristic fallback behavior for first calls, providers without usage, and streams without usage events.
- Invalidate usage baselines when compaction rewrites provider-visible context.
- Feed tracker-backed estimates into context pressure, active context telemetry, post-turn critical checks, and model-switch fit planning.
- Keep the design independent of tokenizer libraries.

**Non-Goals:**

- Adding `tiktoken-rs`, HuggingFace tokenizers, or any local model-specific tokenizer dependency.
- Treating heuristic token estimates as authoritative billing or cost data.
- Persisting detailed per-turn provider usage history in the first implementation.
- Guaranteeing exact preflight context counts for providers that never return usage.
- Redesigning context compaction itself beyond replacing the accounting source it uses.
- Changing `iron-providers` APIs beyond consuming the 0.2.9 usage events already available.

## Decisions

### Add Session-Owned Token Tracking State

Add a session-owned tracker, conceptually:

```rust
struct SessionTokenTracker {
    baseline_input_tokens: Option<usize>,
    delta_tokens_after_baseline: usize,
    accumulated_input_tokens: u64,
    accumulated_output_tokens: u64,
    accumulated_cached_input_tokens: u64,
    accumulated_cache_creation_input_tokens: u64,
    accumulated_cache_read_input_tokens: u64,
    accumulated_reasoning_output_tokens: u64,
    quality: ContextQuality,
}
```

The tracker should expose a snapshot rather than leaking mutable internals. `estimate_current_context()` returns `baseline_input_tokens + delta_tokens_after_baseline` when a baseline exists, otherwise falls back to full provider-visible heuristic estimation.

Rationale: token state belongs to the session, not a single prompt runner loop, because active context telemetry, compaction, and model switching all need the same view.

Alternative considered: keep using `DurableSession::uncompacted_tokens` as the counter and patch it with provider usage. This was rejected because `uncompacted_tokens` is an accumulated heuristic with unclear baseline semantics and cannot represent provider-authoritative totals cleanly.

### Treat Provider Usage as a Request Baseline, Not a Full Turn Baseline

When a usage event arrives for request `N`, set `baseline_input_tokens` to `usage.input_tokens` if present. Do not clear response content already generated by request `N` from future accounting. Assistant text, assistant tool calls, and later tool results are additions after the request baseline and must be counted as delta for request `N + 1`.

Rationale: provider `input_tokens` counted the prompt sent into the model. It did not count the model's response as future input yet.

Alternative considered: clear all delta on every usage event. This undercounts immediately after any assistant response because generated assistant content becomes part of the next request context.

### Count Delta at Durable Append Boundaries

Update the tracker when durable provider-visible entries are appended: user messages, assistant messages, assistant tool calls, and tool results. Reuse the existing text/JSON heuristic for these small deltas.

Rationale: append boundaries already define what may appear in the next provider request. Counting there avoids retaining full duplicate message lists in the tracker.

Alternative considered: store `messages_since_last_api` and estimate the vector on demand. This is simpler conceptually but duplicates transcript state and risks disagreement with actual durable timeline mutations.

### Invalidate Baseline On Provider-Visible Rewrites

Compaction removes and replaces provider-visible context, so it must clear `baseline_input_tokens` and reset delta accounting to a full estimated snapshot until the next usage-bearing response. Other request-envelope changes that alter provider-visible prompt structure outside transcript append flow, such as instruction changes, active skill instruction changes, tool definition changes, or workspace-root prompt changes, should either invalidate the baseline or contribute a conservative estimated delta.

Rationale: the provider baseline only remains valid while the next request is the previous request plus local append-only deltas.

Alternative considered: keep the baseline through compaction and subtract estimated removed ranges. This was rejected because it reintroduces large heuristic error exactly where compaction is supposed to improve context fit.

### Keep Model Switch Baselines Unless Context Is Rewritten

Model switches do not inherently rewrite provider-visible context. Keep the existing baseline through model switches and allow the next usage-bearing response from the target provider/model to resync accounting. Use the target model's context window for pressure and fit calculations.

Rationale: tokenizer differences between model families are expected to be smaller than the configured pressure bucket gaps, and clearing the baseline on every switch would degrade estimates for no structural reason.

Alternative considered: always clear baseline on model switch. This is safer but loses the main benefit of provider-reported accounting during model comparison and switch planning.

### Separate Context Estimates From Cost Totals

Use `input_tokens` plus delta estimates for current context pressure. Use only provider-reported usage fields for accumulated cost-related telemetry. Heuristic deltas should not be added to billing totals.

Rationale: context pressure needs a best-current estimate before the next call. Cost accounting needs provider-authoritative values and should not mix in guessed tokens.

Alternative considered: add estimated deltas to cost totals until provider usage arrives. This was rejected because it would overcount or require later reconciliation.

### Preserve Existing Quality Semantics Initially

Continue using `ContextQuality::Estimated` for baseline-plus-delta snapshots unless the estimate has no local delta and all included categories are provider-derived. Do not add a new quality enum variant in the first pass unless implementation reveals a client-facing need.

Rationale: the existing quality model is coarse, and baseline-plus-delta still includes heuristic components in most useful preflight states.

Alternative considered: add `ContextQuality::ProviderReported`. This may be useful later, but it increases API surface before clients have a clear behavior distinction to consume.

## Risks / Trade-offs

- Usage event ordering may differ by provider or stream mode -> update tracker from usage events independently of output ordering and add tests for non-streaming, streaming final usage, and usage-less streams.
- Delta undercounting after response output would cause premature pressure relief -> explicitly count assistant output/tool calls as post-baseline delta and test multi-step tool round trips.
- Request-envelope changes can make append-only assumptions invalid -> invalidate baseline on known rewrite/configuration boundaries and fall back to full heuristic until resync.
- Providers may omit `input_tokens` but report output tokens -> accumulate output telemetry but do not establish a context baseline without input tokens.
- Existing `uncompacted_tokens` users may conflict with tracker estimates -> migrate pressure decisions to tracker snapshots while keeping old fields only where still needed for compatibility.
- Baseline survives model switch despite tokenizer differences -> pressure thresholds remain bucketed and conservative, and the next usage-bearing response resyncs.

## Migration Plan

The dependency on `iron-providers` 0.2.9 is already available and compatible with a minimal no-op usage handler. Implement tracker support behind existing context-management behavior without changing persisted session formats unless durable storage of aggregate usage is explicitly needed.

Roll back by ignoring `ProviderEvent::Usage` and returning to heuristic-only snapshots; provider events are additive and usage-less behavior remains supported.

## Open Questions

- Should accumulated usage totals live only in memory for the initial implementation, or should they be serialized with durable session state for resume/reporting?
- Should active context telemetry add explicit accumulated usage fields now, or should cost telemetry get a separate API in a later change?
- Which request-envelope changes can occur mid-session today and therefore require explicit baseline invalidation hooks in the first implementation?
